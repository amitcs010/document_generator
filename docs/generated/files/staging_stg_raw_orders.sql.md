# staging/stg_raw_orders.sql

## Component Overview
- **Layer:** Staging
- **Type:** Table (materialized)
- **Schedule:** Daily at 02:00 UTC
- **Owner:** Data Engineering
- **Refresh Strategy:** Full rebuild (DROP and CREATE)

## Purpose
This component ingests raw order transaction data from S3-backed Spectrum tables into Redshift, applying standardized type casting, business rule filtering, and data quality checks. It serves as the single source of truth for downstream analytics, reporting, and BI tools by providing clean, consistently-typed order records within a rolling 3-day window. The staging layer acts as a buffer between volatile source systems and trusted analytical datasets.

## Inputs

- **spectrum.raw_orders** — External Parquet files stored in S3 and queried via Redshift Spectrum. Provides raw order transaction records including customer IDs, order amounts, payment/shipping details, timestamps, and test/system flags. This component depends on this table to access all order events generated by the transactional system.

## Outputs

- **staging.stg_raw_orders** — Cleaned, typed, and filtered order records ready for consumption by mart and reporting layers. Contains 18 columns with standardized data types, resolved nulls, and business rule filtering applied. Consumed by downstream fact tables, dashboards, and ad-hoc analytics queries.

## Key Business Logic

### Type Standardization
All numeric identifiers (`order_id`, `customer_id`) are cast to `BIGINT` to ensure consistency across the data warehouse and prevent join mismatches. Monetary amounts (`total_amount`, `discount_amount`, `tax_amount`, `shipping_amount`) are cast to `DECIMAL(12,2)` to preserve financial precision and avoid floating-point rounding errors in downstream calculations.

### Timestamp Handling
Raw `created_at` and `updated_at` fields are converted to both DATE and TIMESTAMP formats:
- `order_date` (DATE) enables efficient date-based filtering and partitioning in downstream queries
- `order_timestamp` (TIMESTAMP) preserves intra-day ordering and enables time-of-day analysis
- This dual representation reduces the need for repeated conversions in dependent queries

### Null Handling & Defaults
- `coupon_code`: Null values replaced with `'NONE'` to avoid three-valued logic in GROUP BY and JOIN operations; enables accurate coupon adoption metrics
- `order_channel`: Null values default to `'web'` based on business assumption that most orders originate from web channel when channel is not explicitly captured
- These defaults ensure every row has a valid value for segmentation and filtering

### Business Rule Filtering
The WHERE clause encodes three critical business rules:

1. **Rolling 3-day window** (`created_at >= DATEADD(day, -3, GETDATE())`): Limits data to recent orders only, reducing table size and improving query performance. Assumes daily runs will capture all orders; older orders are archived separately. This window is intentionally wider than the daily schedule to handle late-arriving data and backfills.

2. **Test order exclusion** (`is_test = FALSE`): Filters out internal testing, QA, and development orders that would skew metrics. Critical for accurate revenue reporting and customer analytics.

3. **System cancellations exclusion** (`status != 'cancelled_by_system'`): Removes orders cancelled by automated system processes (e.g., fraud holds, payment failures) to focus on legitimate customer transactions. Preserves customer-initiated cancellations for churn analysis.

4. **Positive amount filter** (`total_amount > 0`): Excludes zero-value orders, refunds, and data errors. Ensures all rows represent actual revenue transactions.

### Audit & Lineage
- `_loaded_at`: Populated with `GETDATE()` to record when each row was processed. Enables data freshness monitoring and troubleshooting of stale data issues.

## Data Quality & Edge Cases

### Null Handling Strategy
- **Explicit defaults:** `coupon_code` and `order_channel` are replaced with business-meaningful defaults (`'NONE'` and `'web'`) rather than preserved as NULL. This prevents NULL propagation in downstream GROUP BY operations and ensures every row is usable for segmentation.
- **Implicit NULLs:** `payment_method`, `shipping_method`, `billing_country`, and `shipping_country` may contain NULLs if source data is incomplete. Downstream queries must handle these with `COALESCE()` or `WHERE column IS NOT NULL` filters.
- **Assumption:** The source system guarantees that `order_id`, `customer_id`, `order_date`, and `total_amount` are never NULL. If this assumption breaks, rows will fail to load or produce incorrect results.

### Deduplication Strategy
**No explicit deduplication is performed.** This assumes:
- The source `spectrum.raw_orders` table has a unique constraint on `order_id`
- The rolling 3-day window and daily schedule prevent duplicate ingestion
- If the source system produces duplicate rows (e.g., due to ETL reprocessing), they will appear in this table

**Risk:** If source data contains duplicates, downstream aggregations will overcount. Mitigation: Add `DISTINCT ON (order_id)` or implement a deduplication check if source reliability degrades.

### Business Rule Assumptions
1. **3-day rolling window:** Assumes all orders are captured within 3 days of creation. If orders are backfilled after 3 days, they will be missed. Mitigation: Extend window or implement a separate backfill process.
2. **`is_test = FALSE` flag:** Assumes the source system reliably marks test orders. If this flag is missing or incorrect, test data will contaminate analytics.
3. **`total_amount > 0`:** Assumes refunds and adjustments are recorded as separate negative-amount rows, not as zero-amount orders. If refunds are recorded as zero-amount rows, they will be filtered out.
4. **Country codes:** Assumes `billing_country` and `shipping_country` are always valid ISO 2-letter codes. Invalid codes (e.g., `'XX'`, `'USA'`) will not be caught and may cause downstream join failures.

### Data Integrity Risks
- **Missing customer_id:** If a customer_id is NULL or references a non-existent customer, downstream joins to the customer dimension will fail or produce NULLs.
- **Negative amounts:** The filter `total_amount > 0` prevents negative orders, but does not validate that `discount_amount`, `tax_amount`, and `shipping_amount` are non-negative. Negative shipping or tax could indicate data errors.
- **Timestamp ordering:** If `updated_at < created_at`, it indicates a data quality issue in the source system but is not caught by this query.
- **Status values:** No validation that `order_status` contains only expected values. Invalid statuses will propagate downstream.

## Performance Notes

### Distribution & Sort Keys
- **DISTKEY(order_id):** Distributes rows across Redshift nodes by `order_id`. This is optimal for:
  - Joins to order line items (typically joined on `order_id`)
  - Aggregations by `order_id`
  - Reduces data movement during joins
  - Assumes `order_id` has good cardinality (high number of unique values)

- **SORTKEY(order_date):** Sorts rows by `order_date` within each node. This is optimal for:
  - Range queries filtering by date (e.g., `WHERE order_date >= '2024-01-01'`)
  - Time-series analysis and trend queries
  - Enables zone map pruning to skip blocks of data
  - Assumes most queries filter on date ranges

### Query Execution Implications
- **Full table scan:** The WHERE clause filters on `created_at` (not the sort key `order_date`), so Redshift cannot use zone maps to prune blocks. However, the 3-day window significantly reduces the working set.
- **No indexes:** Redshift does not support traditional indexes. Performance relies on distribution, sort keys, and table statistics (maintained by `ANALYZE`).
- **Table size:** With a 3-day rolling window, this table should contain ~3 days of orders. Assuming 10K orders/day, expect ~30K rows. This is small enough for fast scans and joins.

### Expensive Operations
- **CONVERT(DATE, ...)** and **CONVERT(TIMESTAMP, ...):** Type conversions are relatively cheap in Redshift but are performed on every row. If source data were already typed correctly, these could be eliminated.
- **NVL() functions:** Null checks are fast but add overhead. Minimal impact at this scale.

### Statistics & Optimization
- **ANALYZE:** Executed after table creation to update table statistics (row count, column distributions). This enables the query optimizer to make better decisions in downstream queries. Should be re-run if data distribution changes significantly.

## Dependencies

### Upstream (Must Run Before This Component)
- **spectrum.raw_orders** — External S3 Parquet files must be available and queryable via Redshift Spectrum. Typically populated by a data lake ingestion process (e.g., Fivetran, custom ETL). No explicit dependency on another dbt model, but depends on the source system's data availability.

### Downstream (Components That Depend on This Output)
- **fct_orders** (fact table) — Joins `stg_raw_orders` to build the core orders fact table with additional business logic, surrogate keys, and dimensional joins.
- **dim_order_status** (dimension) — Consumes `order_status` values to build a status dimension.
- **rpt_daily_orders** (report) — Aggregates `stg_raw_orders` to produce daily order counts, revenue, and KPIs.
- **analytics.orders_v1** (BI view) — Exposes cleaned order data directly to Tableau and other BI tools.
- **Ad-hoc queries** — Data analysts query this table directly for exploratory analysis.

### External Dependencies
- **Redshift Spectrum** — Requires active Spectrum configuration and S3 permissions to query `spectrum.raw_orders`.
- **IAM/Security** — Requires `GRANT SELECT` permissions for `analytics_readers` group to be defined in Redshift.
- **Scheduler** — Depends on external orchestration tool (e.g., Airflow, dbt Cloud) to trigger daily at 02:00 UTC.

### Implicit Assumptions
- The `analytics_readers` group exists in Redshift and contains all users/roles that should access order data.
- The source system's timezone is UTC (or the `GETDATE()` calls assume UTC).
- No other process is writing to `staging.stg_raw_orders` during the daily run (DROP TABLE is not concurrent-safe).

## Maintenance & Monitoring

### Known Limitations
1. **Full table rebuild:** The `DROP TABLE IF EXISTS` approach means the entire table is rebuilt daily, which is inefficient for large tables. Consider switching to incremental loads (INSERT/UPDATE) if table size grows beyond 1M rows.
2. **No error handling:** If the source table is unavailable or the query fails, the staging table will be dropped and not recreated, breaking downstream dependencies. Add error handling and rollback logic.
3. **Hard-coded 3-day window:** The rolling window is not parameterized, making it difficult to adjust without code changes.

### Recommended Monitoring
- **Row count trend:** Track daily row counts to detect anomalies (e.g., sudden drop in orders).
- **Load time:** Monitor query execution time to detect performance degradation.
- **Data freshness:** Alert if `_loaded_at` is older than expected (e.g., > 1 hour past 02:00 UTC).
- **Null rates:** Monitor percentage of NULLs in key columns to detect data quality issues.
